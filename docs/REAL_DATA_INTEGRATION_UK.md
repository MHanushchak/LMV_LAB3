# SmartBasket: перехід до реальних даних

Перевірено 18.11.2026. Це результат дослідження й пропозиція реалізації.
Реальні ціни, облікові записи магазинів та оформлення замовлень до застосунку ще не підключено.

## Що підтверджено

| Мережа | Перевірений канал | Висновок для SmartBasket |
| --- | --- | --- |
| Сільпо | Офіційний MCP `https://mcp.silpo.ua/mcp`: OAuth 2.1/PKCE, каталог і кошик авторизованого гостя. Правила забороняють міжмагазинне/міжмережеве порівняння та масове збирання даних. | Для порівняння потрібна окрема домовленість. Канал можна розглядати для окремого помічника покупок у межах дозволеного використання. [Офіційна документація](https://ai-factory.silpo.ua/) |
| ATB | Є офіційний онлайн-магазин, вибір магазину/отримання; остаточна ціна може змінитися під час комплектації. | Публічну підтримувану документацію API для стороннього порівняння або перенесення кошика не підтверджено. Відсутність знайденої документації не означає відсутності приватного API.
Знайдені сторонні бібліотеки та згадки старих API не прийнято за підтвердження
підтримуваного нині інтеграційного контракту.

Додаткова технічна перевірка без входу в акаунт: GET
`https://mcp.silpo.ua/.well-known/oauth-authorization-server` повернув HTTP 200,
публічні адреси authorize/token/register та підтримку S256. Це перевірка
метаданих, а не авторизованого доступу до товарів чи успішного перенесення кошика.
Вхід, реєстрація клієнта й операції з кошиком не виконувалися.

Ціни Сільпо залежать від вибраної адреси/магазину за офіційними
[правилами інтернет-продажів](https://silpo.ua/service-agreement).
Тому одного поля «Львів» із поточного прототипу недостатньо для точного порівняння.

## Рекомендований шлях

Спершу — невеликий погоджений фід одного магазину та 10–20 вручну перевірених SKU.
Для повноцінного «Де дешевше» потрібні щонайменше два джерела, які допускають
показ і зіставлення цін. Отримання HTTP-відповіді саме по собі не підтверджує
умови використання даних.

| Варіант | Як реалізувати | Що потрібно з’ясувати |
| --- | --- | --- |
| Партнерський API | Серверний адаптер → нормалізовані пропозиції → порівняння | Доступ, права на порівняння/кешування, ліміти, SKU та branch ID, sandbox |
| Погоджений CSV/JSON-фід | Серверний імпорт із перевіркою структури й журналом помилок | Частота оновлення, регіон/магазин, залишки, строк придатності даних |
| Офіційна інтеграція кошика | Окремий адаптер експорту після вибору товарів і підтвердження | Авторизація, одиниці кількості, ідемпотентність, повернення checkout URL |
| Перехід на сайт | Верифіковане посилання на товар/магазин | Не позначати як автоматичне перенесення; generic URL не переносить SKU/кількість |
| Парсинг HTML | Лише як погоджений обмежений експеримент | Доступність розмітки, зміни HTML, прив’язка до локації, умови джерела |

Не рекомендується починати з прихованих endpoint-ів сайту: їхній формат,
авторизація, ліміти та стабільність не підтверджені контрактом. Проксі усуває
частину браузерних обмежень, але не вирішує питання даних, сесій і дозволів.

## Що змінити в коді

Зараз `src/features/catalog/catalog.ts` поєднує опис товару та фіксовані пропозиції
трьох мереж; `compare/model.ts` синхронно обчислює кошики з цього масиву.
Це зручно для відтворюваних сценаріїв, але не є live-інтеграцією.

Запропонована схема:

1. **Product** — канонічний товар із GTIN, брендом, фасуванням та одиницею.
2. **RetailerProductMapping** — зв’язок канонічного товару з конкретним SKU мережі;
   статус `verified/unverified`. Назви «молоко» недостатньо: потрібні жирність,
   об’єм, бренд і варіант. Невпевнені збіги потребують вибору користувача.
3. **OfferSnapshot** — ціна упаковки, валюта, залишок, магазин, спосіб отримання,
   час перевірки, джерело та строк актуальності. Відсутня ціна — `null`, не 0.
4. **RetailerAdapter** — `searchProducts`, `getOffers`, `getLocations`;
   `exportCart` лише за підтримки мережі. Перед роботою перевіряти capabilities
   джерела: читання, порівняння, експорт.
5. **Comparison service** — бере перевірені snapshots, рахує цілі упаковки,
   відокремлює неповний кошик, невідомий залишок і помилку джерела.
6. **UI** — показує час оновлення та зміну суми; при відмові джерела пропозиція
   стає недоступною/застарілою, а не непомітно замінюється сценарною ціною.

Приклад цільового контракту (пропозиція, ще не реалізований live-provider):

```ts
type OfferSnapshot = {
  retailerId: "atb" | "silpo" | "varus";
  retailerProductId: string;
  canonicalProductId: string;
  branchId: string;
  fulfillment: "pickup" | "delivery";
  packQuantity: number;
  unit: "kg" | "L" | "pcs";
  packPriceCents: number | null;
  currency: "UAH";
  availability: "in-stock" | "out-of-stock" | "unknown";
  productUrl: string;
  fetchedAt: string;
  expiresAt: string;
  priceCondition: "regular" | "promotion" | "loyalty";
};
```

Ключ кешу має враховувати мережу, SKU, магазин, спосіб отримання та умови ціни.
TTL узгоджується з джерелом; прострочені дані не повинні отримувати позначку
«Найвигідніше». Тарифи доставки, мінімальне замовлення та додаткові збори
показуються окремо від вартості товарів. Порівнювати потрібно однакові умови.

## Сервер, авторизація та перенесення

План для наявного Next.js-проєкту: Route Handlers для пошуку й порівняння,
серверні адаптери джерел, БД для mappings/snapshots і черга обмежених оновлень.
До клієнта передавати тільки нормалізовані результати. Ключі й токени — серверно,
із відокремленням сесій користувачів. Адреси — лише в контексті конкретного
користувача; їх не можна включати в загальний кеш пропозицій.

Експорт не повинен автоматично очищати наявний кошик мережі. Потрібний попередній
перегляд: товар, кількість/упаковки, заміни, стара й нова сума. Повторний запит
після таймауту не має додавати товари вдруге: перевірка результату та
узгоджена з API ідемпотентність. Завершення покупки залишається на checkout
магазину. Сам факт додавання в кошик не означає оформлення замовлення.

## Послідовність переходу

| Етап | Конкретний результат | Умова завершення |
| --- | --- | --- |
| 0 — сценарії | Ізольовані fixtures і 4 відтворювані потоки | Готово в поточній зміні; звичайні дані не перезаписуються |
| 1 — джерело | Погоджений API/фід та 10–20 зіставлених SKU одного магазину | Читання цін/залишків перевірене; зафіксовано права й ліміти |
| 2 — live-перегляд | Нормалізовані ціни з часом оновлення та станами помилок | Немає fallback до fixtures; тестуються 401/429/timeout/застарілі дані |
| 3 — порівняння | Друге дозволене джерело й однакові умови фасування/локації | Контрольні кошики перевірено проти джерел |
| 4 — експорт | Попередній перегляд → підтвердження → кошик магазину | Перевірено повторні запити, зміни цін і часткові збої |

Не варто оцінювати строки партнерського доступу як строки програмування.
Після отримання технічного контракту можна окремо оцінити адаптер і міграцію.
Наступний практичний крок: узгодити тестовий фід із правом порівняння або надати
власний CSV/JSON із відомими SKU та магазином. До цього моменту залишаються
окремі сценарні дані й технічна документація про їхні межі.
